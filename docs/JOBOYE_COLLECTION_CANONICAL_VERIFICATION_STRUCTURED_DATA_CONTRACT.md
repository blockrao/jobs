# JobOye Collection → Canonical Data → Verification → Structured Data Contract v1

**Status:** Proposed contract for review; this document does not apply migrations, change production schemas, or authorize public publication.  
**Scope:** FJA is an internal discovery input only. JobOye's canonical records and public pages must not identify FJA as the source or expose FJA article IDs/URLs.  
**Workbook contract:** exactly two main sheets: `Recruitments` and `Posts`.

## 1. Product objective

JobOye is building a complete, precise, source-verified employment-opportunity dataset—not a copy of an aggregator's article catalogue. Collection maximizes coverage; normalization creates stable entities; official-source enrichment verifies facts; publication and structured data expose only records that pass explicit quality gates.

The pipeline is:

1. **Collect** the source article and preserve an immutable source capture.
2. **Normalize** recruitment and post entities, retaining all substantive source-supported content.
3. **Verify/enrich** facts against the official notification and other authoritative sources, recording evidence and conflicts.
4. **Publish** approved canonical records through JobOye pages and structured data, with automated tests.

Collection is not canonical publication. An item without a verified official notification remains in the internal inventory; it is not discarded, but it is blocked from promotion until the official source requirement is met.

## 2. Entity and workbook model

### Sheet A — `Recruitments`

One row per distinct recruitment notice / recruitment event. Suggested stable key: internal inventory ID plus source-specific external identity kept in private collection metadata. Do not use a third-party article ID as JobOye's canonical entity ID.

Core columns (exact workbook headers are defined in Section 4):

- Recruitment key and import action
- Organization name and canonical organization match, if resolved
- Official notification/advertisement number and official notification URL
- Recruitment title/type and explicit recruitment-level vacancy total
- Recruitment-wide dates, application method and application URL
- Recruitment-wide fee, selection, document and application instructions
- Source-capture references and extraction outcome
- Official-verification/enrichment state and review notes
- Unmapped recruitment-level source payload

### Sheet B — `Posts`

One row per distinct post/role within a recruitment. Every row must carry `recruitment_key` as a foreign-key/import reference to the parent row.

- Post key and recruitment key
- Post title and explicit post-specific vacancy count
- Qualification, essential/desirable conditions and experience
- Age minimum/maximum, reference date and relaxation rules
- Salary amounts, currency, period and original pay wording
- Employment arrangement, tenure, location, duties/responsibilities
- Post-specific dates, fee/application/selection conditions where applicable
- Evidence references, verification state and unmapped post payload

Do not create a post merely because a title-like phrase exists. When decomposition is ambiguous, create a review candidate only if useful, mark it unresolved, and never treat it as a verified canonical post.

### Repeated or complex data

Two sheets are the human import interface, not a requirement to flatten every one-to-many relation into a single scalar column. Use JSON arrays in the workbook for repeated events/rules where necessary, and retain normalized internal support records for source observations, immutable captures and field-level evidence. If a repeated structure becomes frequently queried, validated or independently versioned, give it a relational table rather than allowing JSON to become a permanent substitute for the domain model.

## 3. Identity, provenance and public-data boundary

- Keep collection/source identifiers, source URLs, source-reported values, capture timestamps and hashes in private inventory/provenance records.
- Keep the official notification and official application URLs distinct. An application page is not automatically the official notification.
- Keep raw FJA capture and raw official-notification capture separate and immutable. Store normalized text separately from original HTML/PDF bytes.
- Do not expose FJA names, article URLs, article IDs, or source-specific metadata in public JobOye canonical fields, page copy, breadcrumbs, Schema.org JSON-LD, sitemaps or public APIs.
- Internal provenance is retained for auditability; this policy does not mean deleting evidence or pretending an internal discovery source was an official source.
- Canonical IDs and slugs are generated by JobOye's entity rules and are not derived from source branding.
- If source-reported and official values disagree, preserve both, record the conflict and use the verified value only after review. Never silently overwrite evidence.

### Standard normalization rules

- Dates use ISO `YYYY-MM-DD`; timestamps include timezone.
- Counts are integers; unknown stays NULL, not zero.
- Money is numeric with a currency code and an explicit period. Preserve original wording. Do not annualize or otherwise convert unless a documented rule requires it.
- Age bounds and reference dates remain null when unstated. Do not infer minimum age zero.
- Keep source-reported, normalized, and officially verified values distinct; use field evidence to connect them.
- Do not use a subjective extraction-confidence score. Track extraction outcome and factual verification separately.
- A shared fact may be inherited by a post only when the official/source material makes its scope clear; record that scope rather than copying blindly.

## 5. Verification and enrichment contract

Verification is field-level and source-aware. Suggested internal states:

- `PENDING`: not reviewed against the official source.
- `VERIFIED`: directly supported by the cited official evidence.
- `CONFLICT`: sources disagree; needs resolution.
- `NOT_FOUND`: sought but not found in reviewed official material.
- `NOT_APPLICABLE`: field does not apply to this entity.
- `NEEDS_REVIEW`: ambiguous wording, unclear scope or unresolved interpretation.

These are proposed workflow states; reconcile them with existing database enums before migration. Do not overload the crawler's `detail_status` (`EXTRACTED/PARTIAL/FAILED/PENDING`) with these verification states.

For every material fact, evidence should identify: entity key, optional post key, field path, source type, source URL/document capture, page/section/table, short evidence excerpt, capture timestamp/hash, reviewer or process, verification state, and conflict/review note. FJA evidence remains labelled as internal discovery/source-reported evidence; the official notification is the verification basis.

Enrichment may normalize or explain a fact but must not overwrite immutable source captures or claim that an interpretation is verbatim source wording.

## 6. Structured-data contract

### Principle

Generate Schema.org/Google structured data from the **verified canonical post and its public page**, not directly from the FJA inventory and not from a separately maintained hand-written JSON-LD object. The visible page content and JSON-LD must agree.

Authoritative references to validate during implementation:
- Google JobPosting structured data: https://developers.google.com/search/docs/appearance/structured-data/job-posting
- Google general structured data policies: https://developers.google.com/search/docs/appearance/structured-data/sd-policies
- Schema.org JobPosting: https://schema.org/JobPosting

### Candidate field mapping

| Canonical concept | Structured-data mapping | Guardrail |
|---|---|---|
| Post title | `JobPosting.title` | Use actual job title, not a keyword-stuffed SEO title |
| Full job description | `JobPosting.description` | Substantive HTML/text, consistent with visible page; do not output only a thin summary |
| Original publication date | `JobPosting.datePosted` | Use a supportable date; don't substitute crawl date |
| Application deadline | `JobPosting.validThrough` | Only if explicit and valid; update/expire pages when deadline passes |
| Employment arrangement | `JobPosting.employmentType` | Map to supported Schema.org values only when source evidence supports it |
| Hiring organization | `JobPosting.hiringOrganization` | Use canonical organization; never use the aggregator as employer |
| Work location | `JobPosting.jobLocation` | Use actual work location; distinguish remote/hybrid and multiple locations correctly |
| Remote-only role | `JobPosting.jobLocationType` plus location requirements as applicable | Use `TELECOMMUTE` only when genuinely fully remote and policy requirements are met |
| Pay | `JobPosting.baseSalary` / `MonetaryAmount` / `QuantitativeValue` | Numeric value, currency and valid unit; no invented annualization |
| Official job/advertisement identifier | `JobPosting.identifier` (`PropertyValue`) | Use employer/official identifier when available; never use FJA article ID |
| Qualifications/experience | Supported JobPosting properties such as `educationRequirements`, `experienceRequirements`, `qualifications` | Use only where semantics and current Google guidance support the mapping |
| Organization identity | `hiringOrganization.sameAs` or `url`, when appropriate | Link to the employer's official identity, not the discovery aggregator |

This is a candidate mapping, not a claim that every field is required or eligible for a Google rich result. Validate required/recommended fields and accepted value formats against Google's current documentation before release. Do not invent values for schema completeness.

### Page-level and policy rules

- One individual job detail page should represent one specific job opportunity and emit its matching `JobPosting` object. Recruitment hubs or role/category listings must not emit a misleading `JobPosting` for multiple distinct jobs.
- The JSON-LD must describe the visible content on that page and meet Google's general structured-data policies.
- Do not emit `JobPosting` when the page does not qualify as an individual job detail page, when material required information is missing, or when the opportunity is expired/removed and the page has not been correctly updated.
- Keep canonical URLs, title, visible details, sitemap state and structured data consistent. Test both valid schema syntax and semantic correctness.
- Internal source capture IDs, FJA URLs, FJA names, extraction statuses, verification workflow notes and private evidence must never be serialized into public structured data.
- Structured data is not a way to guarantee ranking or rich-result display. The objective is accuracy, machine readability, policy compliance and useful information.

## 7. Proposed internal storage layers

The workbook stays at two sheets. The internal system can have more supporting tables because these are different concerns:

1. `fja_job_inventory`: one source article/recruitment candidate; current observed snapshot and internal source metadata.
2. `fja_post_inventory`: source-specific post candidates linked to `fja_job_inventory`, with typed raw fields, unresolved payload, extraction state and official-verification state. The migration is included in the implementation branch and must be applied before running the updated crawler. This table is distinct from canonical `posts`.
3. `source_observations`: append-only hash/version history for changed source content.
4. `fja_source_captures`: append-only original FJA HTML captures keyed by source identity and HTML SHA-256; this supplements the 90-day workflow artifact and preserves historical source versions in the database.
5. Field evidence/verification records: normalized field path, source capture, excerpt, reviewer/state and conflicts. The current post inventory retains candidate-level evidence payloads, but a consistent field-level verification model across all entity types remains follow-up work.
6. Existing canonical JobOye organization/recruitment/post entities: populated only through a reviewed promotion workflow, never by the discovery crawler directly.

The two source-inventory migrations must be applied before the updated crawler runs. The inventory post table must not be confused with canonical `posts`. Raw official-notification PDF capture remains a separate verification-stage requirement; the current immutable capture implementation covers the source article HTML.

## 8. Quality gates and automated tests

Before scaling collection or publishing any schema changes, verify:

- Stable source identity and idempotent re-runs.
- Recruitment/post parent integrity and no cross-post leakage.
- Source totals versus post totals reconcile where logically expected; do not force totals to match if the notice distinguishes categories/backlog/other buckets.
- Unknown values stay null; no fabricated defaults.
- All unmapped substantive source content is preserved.
- Official and application URLs remain distinct.
- FJA discovery provenance never leaks into public canonical fields, pages, JSON-LD, sitemap or API payloads.
- Official conflicts remain visible until resolved.
- Structured data is generated from the same canonical post fields rendered on the page.
- One post detail page emits one valid `JobPosting`; hub pages do not.
- Required structured-data values are not invented; expired opportunities are handled correctly.
- Workbook rows, inventory records, source observations and run ID reconcile.
- Repeated unchanged source content creates no duplicate observation; changed content preserves historical capture.
